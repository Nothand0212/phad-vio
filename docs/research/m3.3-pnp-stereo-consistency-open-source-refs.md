## 1. 问题与证据边界

已证根因不是 PnP 求解失败本身，而是现有实现把「左目 RANSAC 有足够 inliers」
直接解释为「候选位姿可进入 stereo 后端并授权本帧掩码与后续 landmark 生命周期
变更」。MH_02 source i=364 反例中：

- PnP 有 26 个左目 inliers；
- 候选相对恒速 guess 偏离约 `11.149 m / 2.960 rad`；
- PnP 路径优化前 stereo RMS 为 `180.552 px`，不用 PnP 时为 `2.121 px`；
- 错误中间状态随后永久删除关键 landmark，形成完整发散链。

本次只回答三个问题：

1. PnP 是否应视为待验证 proposal，而不是单凭求解成功就采用；
2. 验证应使用 SE(3) 固定阈值，还是系统实际消费的 stereo measurement；
3. 仲裁应归属 frontend、apps 还是 estimator。

## 2. GTSAM：后端真实合同是三维 stereo residual

`examples/StereoVOExample.cpp` 和 `StereoVOExample_large.cpp` 都把 rectified stereo
观测建模为 `StereoPoint2(uL, uR, v)`，用
`GenericStereoFactor<Pose3, Point3>` 共同优化 pose 与 landmark。它没有 PnP
仲裁示例，但明确了 VO 后端实际消费的 measurement space。

`gtsam/slam/StereoFactor.h:126-153` 的 `evaluateError()`：

- 由 candidate pose（含可选 `body_P_sensor`）构造 `StereoCamera`；
- 投影 world point；
- 返回 `(uL, uR, v)` 的三维预测减观测；
- cheirality 不能产生正常 residual；默认返回大罚值，配置后也可抛异常。

**事实**：只验证左目 `(uL, v)` 会漏掉 `uR`，也就漏掉 disparity / depth
一致性；这正是 MH_02 反例暴露的证据缺口。

**对 PHAD 的含义**：若要判断一个 PnP proposal 是否适合作为当前 GTSAM graph 的
初值，最贴合既有合同的量是同一批 shared landmark 上的 stereo residual，而不是
另造只在 SE(3) 空间成立的距离阈值。

## 3. ORB-SLAM3：PnP 是 proposal，stereo pose optimization 才决定采用

`src/Tracking.cc:3609-3763` 的 `Relocalization()` 不是把 MLPnP RANSAC 结果直接
视为成功：

1. RANSAC 先给 candidate pose 和初始 inlier mask；
2. `Optimizer::PoseOptimization()` 用 candidate 初始化 pose-only optimization；
3. 优化后的 `nGood < 10` 立即拒绝；不足 50 时继续投影搜索、重新优化；
4. 最终 `nGood >= 50` 才宣布 relocalization 成功；optimizer 标出的 outlier 才从
   当前帧关联中断开。

`src/Optimizer.cc:814-1169` 对 rectified stereo observation 创建
`EdgeStereoSE3ProjectXYZOnlyPose`，measurement 为 `(uL, v, uR)`，使用三维 chi2
阈值 `7.815`，并在多轮优化间重新分类 inlier/outlier。

**可借鉴事实**：PnP 的 inlier 数只是候选生成阶段的证据；采用前还要经过与最终
观测模型一致的验证。ORB-SLAM3 选择完整 pose-only optimization，PHAD 当前修复片
不必复制其搜索和多轮 BA，但不应跳过 stereo 证据。

## 4. VINS-Fusion：先给初值，永久外点处理放到完整优化之后

`vins_estimator/src/estimator/feature_manager.cpp:215-295` 的
`initFramePoseByPnP()`：

- 以前一帧相机位姿为 guess；
- 用历史 3D 与当前左目归一化 2D 调 `solvePnP`；
- 成功后只写当前 pose 初值；失败则保留已有上一帧位姿。

热路径随后执行 triangulation 和完整 optimization；
`vins_estimator/src/estimator/estimator.cpp:1511+` 的 `outliersRejection()` 再按各帧
重投影误差处理外点，stereo observation 会同时计算左、右相机误差。

**可借鉴事实**：VINS 没有实现「PnP 与 guess 二选一」的显式仲裁，但它没有让
PnP 的左目结果在完整 stereo 优化前直接永久删除 landmark。其执行顺序支持把
proposal acceptance 与不可逆 lifecycle mutation 分开。

## 5. Kimera-VIO：相近的弱门控与额外位姿门控

`src/frontend/Tracker.cpp:1064-1288` 的 PnP 从 backend landmark map 与当前 bearing
构造 2D-3D RANSAC，可选使用 rotation/pose prior；
`src/frontend/VisionImuFrontend.cpp:146-174` 只用求解成功和
`inliers > min_pnp_inliers` 设 `TrackingStatus::VALID`，并留有“不移除 PnP
outliers”的 TODO。

这与 PHAD 当前「左目 PnP + inlier 数」门控接近，因而不能作为其充分性的证据。
Kimera 在 loop closure 的另一条 PnP 路径
`src/loopclosure/LoopClosureDetector.cpp:907-942` 还会对 translation norm 设置上限，
说明工程上会在 RANSAC 之外审查 candidate；但该固定上限服务 loop closure，不能
直接移植为逐帧 VO 的 SE(3) 阈值。

## 6. 综合结论

### 已有实现共同支持的部分

- PnP/RANSAC 输出应理解为 proposal；inlier 数不是最终观测模型的一致性证明。
- stereo 系统在 pose refinement / outlier classification 中使用包含左右目的观测。
- candidate 验证与 landmark 生命周期变更应分阶段；验证失败不应应用 proposal 的
  inlier mask。

### 没有可直接照搬的部分

未发现上述实现逐帧计算「PnP proposal stereo score vs constant-velocity guess stereo
score」并择优。因此该比较规则是基于 PHAD 已复现反例作出的工程推断，不应描述成
开源实现的既有做法。

### 对 PHAD 的最小切片建议

1. 保持 `phad::estimator` 所有权：只有 estimator 同时拥有窗口活点
   `landmarks_W`、rectified stereo calibration、恒速 guess、候选位姿和后续
   graph/lifecycle mutation；frontend 与 apps 均缺少这组合同。
2. `tryPnpInit()` 只生成 proposal 与左目 RANSAC inlier indices；在任何观测掩码、
   新点 backprojection 或永久 lifecycle 变更前，对 proposal 与 guess 使用同一批
   shared stereo constraints 评分。
3. 采用 proposal 的必要条件应至少包括：求解成功、位姿有限、inlier 足够、stereo
   score 未显著劣于 guess；本片以既有 `stereo_sigma_px` 作为统计等价带。否则完整
   fallback 到 guess，且不应用 PnP inlier mask。
4. 不新增 public API、配置项或 config hash。`pnp_success` 继续表示“本帧实际采用
   PnP”，仲裁失败沿用既有 fallback 语义。
5. 首个回归测试通过 public `StereoVoEstimator::update()` seam 构造“左目支持错误
   PnP、disparity 支持 guess”的确定性场景，不暴露 private scoring hook。

SE(3) 固定差异门限只能检测“大跳”，但引入平移/旋转双单位、场景尺度和速度依赖；
把仲裁放到 apps/frontend 则会复制 estimator 私有状态或反向耦合。因此两者只作为
备选，不作为推荐边界。
