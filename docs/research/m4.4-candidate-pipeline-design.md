## 1. 当前决策问题

P1 已证明 installed GTSAM fixed-lag lifecycle 能在 production graph events 条件下有界运行，
但它共享 production tracker、keyframe schedule、landmark admission/cull 与初值，因而不是
可计算 candidate ATE 的系统反事实。

P2 的目标是建立一条 read-only、candidate-owned 的完整闭环：

```text
immutable rectified stereo + IMU interval
                  |
                  +---------------- production existing pipeline
                  |
                  +---------------- candidate-owned pipeline
                                      |
                                      +-- tracker / ids
                                      +-- KF gate / accepted schedule
                                      +-- estimator / graph / prior
                                      +-- landmark / cull / drop
                                      +-- reset / trajectory / diagnostics
```

candidate 结果绝不反馈 production。只有 candidate 自己接受的 `T_W_B` 能进入 candidate
trajectory；禁止在失败处拼接 production pose、bias、map 或 prior。

## 2. 已确认的 module seam

采用同进程方案，seam 位于 `apps` composition root 的 rectification 与 IMU packetization
之后：

- production 与 candidate 只共享只读 rectified `StereoFrame`、IMU samples、
  `t_prev`、`imu_gap`、静态 calibration/config；
- candidate 独占 `StereoTracker`、`LandmarkId` allocator、`KeyframeEpochGate`、
  concrete estimator、fixed-lag graph/marginal prior、landmark/cull/drop/zombie state、
  reset lifecycle、trajectory 与 diagnostics；
- GTSAM 继续留在 estimator PIMPL/PRIVATE link；candidate public header 只出现 Eigen/POD
  和既有领域类型；
- 所有依赖均为 in-process，不增加 port、adapter、mock interface 或 generic
  `Optimizer`；
- 当前只覆盖离线、单线程、严格按 timestamp 顺序的调用，不外推实时并发等价性。

该 seam 的 deletion test 成立：删除 candidate module 后，tracker → gate → estimator →
drop → trajectory 的完整状态机会重新散回 `OfflineVoSession`，因此 module 有真实 depth，
不是 pass-through。

## 3. Design It Twice 对照

### 3.1 方案 I：最小双入口

```cpp
CandidateProcessResult process( const CandidateFrameInput& input );
CandidateFinishResult finish() &&;
```

每帧返回 candidate status、pose、KF epoch、cull/drop 等详细结果；`finish()` 返回最终
trajectory/counts。

优点：typed error 清楚，caller 可即时记录每帧状态。缺点：caller 学会了过多内部诊断，
并可能自行重建 trajectory/counts；interface 有变浅趋势。

### 3.2 方案 II：通用 branch recipe

```cpp
ClosedLoopVoBranch::create( BranchRecipe recipe, BranchOptions options );
BranchResult<BranchFrame> process( const RectifiedStereoImuView& input );
BranchResult<BranchRun> finish();
```

用闭集 variant 暴露 rolling-batch/fixed-lag recipe，并返回完整 `FrameTracks`、KF trace、
backend trace。

优点：same-implementation twin、candidate perturbation 与 fixed-lag 共用一个 interface。
缺点：把 backend variation 变成 public interface，泄漏 `FrameTracks` 与 graph trace；这与
ADR-0001“不创建通用 Optimizer interface”以及当前只有一个最终 candidate 的事实冲突。
该方案不采用。

### 3.3 方案 III：面向 caller 的原子 pipeline

```cpp
CandidateCreateResult CandidatePipeline::create( ... );
CandidateProgress process( const CandidateFrameInput& input );
CandidateRunResult finish() &&;
```

caller 每帧只调用一次 `process()`；module 内部原子执行 input validation、pending-drop
flush、tracking、KF decide、measurement glue、estimator update、KF resolve、cull/drop
feedback 与结果聚合。每帧 diagnostics 与 trajectory 均由 module 自己保存，caller 在
EOS 后一次取回。

优点：interface 最贴近 `OfflineVoSession` 的真实需求，depth、leverage 与 locality 最好；
candidate failure 可停止 candidate 而 production 继续到 EOS。缺点是 module implementation
较大，且整条 candidate 约增加一份 tracker/graph 计算与内存。

## 4. 推荐 interface

推荐方案 III，并吸收方案 I 的 typed terminal error 与 rvalue `finish()`。以下是待确认的
public seam，不是已实施代码：

```cpp
namespace phad::apps
{

  struct CandidateTrackPolicy
  {
    bool drop_culled_tracks   = true;
    int  skip_drop_min_culled = 4;
    int  zombie_drop_age      = 5;
  };

  struct CandidatePipelineOptions
  {
    frontend::StereoTrackerOptions tracker;
    estimator::EstimatorOptions    estimator;
    CandidateTrackPolicy           tracks;
  };

  struct CandidateFrameInput
  {
    const sensor::StereoFrame&              rectified;
    std::span<const sensor::ImuMeasurement> imu_samples;
    common::Timestamp                       t_prev{ 0 };
    bool                                    imu_gap = false;
  };

  enum class CandidateProgress : std::uint8_t
  {
    kRunning = 0,
    kTerminalFailure = 1
  };

  struct CandidateRunResult
  {
    std::optional<common::Trajectory> trajectory;
    std::optional<common::Trajectory> keyframe_trajectory;
    std::vector<CandidateFrameDiagnostics> diagnostics;
    CandidateCounts counts;
    std::optional<CandidateError> error;
  };

  class CandidatePipeline
  {
  public:
    [[nodiscard]] static CandidateCreateResult create(
        camera::RectifiedStereoCalibration calibration,
        CandidatePipelineOptions options );

    ~CandidatePipeline();
    CandidatePipeline( CandidatePipeline&& ) noexcept;
    CandidatePipeline& operator=( CandidatePipeline&& ) noexcept;
    CandidatePipeline( const CandidatePipeline& ) = delete;
    CandidatePipeline& operator=( const CandidatePipeline& ) = delete;

    [[nodiscard]] CandidateProgress process(
        const CandidateFrameInput& input );

    [[nodiscard]] CandidateRunResult finish() &&;

  private:
    struct Impl;
    std::unique_ptr<Impl> m_impl;
  };

}  // namespace phad::apps
```

`CandidateFrameDiagnostics` 是最终验收所需的稳定结果合同，而不是把
`frontend::FrameTracks`、`VioUpdateResult` 或 GTSAM factor types 直接透传。其具体字段在
“错误与诊断”段单独确认。

## 5. 调用与 ordering 合同

```cpp
auto candidate = CandidatePipeline::create( rectified_cal, candidate_options );

while ( auto packet = nextPacket() )
{
  auto rectified = rectifier.rectify( packet.frame );

  runProductionFrame( rectified.value(), packet );

  if ( candidate_running )
  {
    candidate_running =
        candidate.value().process( CandidateFrameInput{
            .rectified   = rectified.value(),
            .imu_samples = packet.samples,
            .t_prev      = packet.t_prev,
            .imu_gap     = packet.imu_gap,
        } ) == CandidateProgress::kRunning;
  }
}

CandidateRunResult candidate_run =
    std::move( candidate.value() ).finish();
```

ordering/invariant：

1. `CandidateFrameInput` 仅在同步 `process()` 调用期间借用；module 不保留 image/span
   alias，也不修改输入。
2. frame timestamp 严格递增；首帧与后续 IMU 区间语义完全复用 sync 的既有合同，不在
   candidate 内发明第二套 packet 规则。
3. `process()` 单线程、不可重入；每个有效输入恰好产生一行 candidate diagnostics。
4. `kRejected` 是正常 estimator outcome，candidate 可继续；graph/marginal prior、slot、
   timestamp、transaction 或 numeric invariant 失败是 terminal。
5. terminal failure 后不再处理 candidate input；production 继续到 EOS。失败 run 保留
   diagnostics/error，但不给出可参与 ATE 的 candidate trajectory。
6. reset 只能来自 candidate 自己的已定义 segment lifecycle，必须记录 reason；不得复制
   production state。
7. `finish() &&` 只调用一次，验证 candidate accepted `T_W_B`、KF trajectory、timestamp、
   counts 与 diagnostics 一致性。

## 6. 明确拒绝

- 不在 `FrameTracks` 后分叉并声称 whole-pipeline candidate；
- 不把 P1 fixed-lag shadow pose 直接 handoff 给 production；
- 不公开 rolling-batch/fixed-lag enum、recipe、`IOptimizer` 或 estimator factory；
- 不公开 `decide()/resolve()`、drop/zombie table 或 factor-slot ledger；
- 不让 caller 聚合 candidate trajectory，避免把 failed/rejected frame 拼成伪成功；
- 不把 candidate writer/I/O 放进本 module；落盘与 ATE/RPE 留在 bench composition root；
- 不为 candidate failure 加 batch fallback、production pose fallback 或 silent reset。

## 7. 分片顺序（待后续段落确认）

1. seam tracer：PIMPL 暂时拥有第二套现行 tracker/gate/batch estimator；同输入 twin 的
   schedule、tracks lifecycle、status、`T_W_B` 与 trajectory 必须一致，且 candidate on/off
   不改变 production artifacts；
2. candidate-only perturbation：只扰动 candidate 的一帧输入，允许其后续递归分叉，同时
   production 继续与 solo control 逐字节一致；
3. 用唯一 concrete fixed-lag implementation 替换 candidate PIMPL 内临时 batch estimator，
   删除临时 twin code，不留下 backend switch/compatibility path；
4. 通过 synthetic lifecycle 与 MH_01 structural gate 后，candidate trajectory 才进入
   ATE/RPE；VIO 必须严格优于 matched VO 才扩 sentinel/full suite。

## 8. 错误与诊断候选（待确认）

### 8.1 两层失败语义

推荐把失败分成两个层级，不能用一个 `bool success` 混合：

1. **frame outcome**：`estimator::UpdateStatus::{kOk,kRejected,kFailed}`。`kRejected`
   是正常观测结果；`kFailed` 只有在 estimator 完整 rollback 后才可继续下一帧。二者都
   写 candidate diagnostics，且不从 production 借状态。
2. **terminal pipeline error**：输入合同、tracker/KF transaction、fixed-lag graph、
   factor-slot/timestamp、rollback 或 trajectory invariant 失败。记录第一个错误后立即停止
   candidate；production 继续到 EOS，但 candidate 不再产出可参与 ATE 的 trajectory。

frame-level `kFailed` 不等于精度门通过。bench 必须独立要求 `failed == 0`、coverage/
completion 达门后，才允许使用完整 candidate trajectory；pipeline module 不内置 dataset
验收政策。

### 8.2 typed terminal error

```cpp
enum class CandidateErrorCode : std::uint8_t
{
  kInvalidConfig = 0,
  kInputContract = 1,
  kPipelineInvariant = 2,
  kEstimatorInvariant = 3,
  kTrajectoryInvariant = 4
};

struct CandidateError
{
  CandidateErrorCode                code;
  std::optional<std::uint64_t>      frame_index;
  std::optional<common::Timestamp>  timestamp;
  std::string                       detail;
};
```

`detail` 保留具体 nested cause；不得只返回枚举而丢失 GTSAM/输入字段/不变量上下文。
create-time 非法配置返回 `kInvalidConfig`，不用构造一个半有效 object。terminal error sticky，
后续 `process()` 不得 reset/reseed 后继续冒充同一 candidate run。

### 8.3 稳定的 per-frame diagnostics

`CandidateFrameDiagnostics` 只公开验收需要观察的行为，不透传 `FrameTracks`、
`VioUpdateResult` 或 GTSAM object：

```cpp
enum class CandidateResetReason : std::uint8_t
{
  kNone = 0,
  kBootstrap = 1,
  kSegment = 2
};

struct CandidateState
{
  Eigen::Isometry3d              T_W_B = Eigen::Isometry3d::Identity();
  std::optional<Eigen::Vector3d> velocity_W;
  Eigen::Vector3d                bias_gyro = Eigen::Vector3d::Zero();
  std::optional<Eigen::Vector3d> bias_acc;
};

struct CandidateFrameDiagnostics
{
  std::uint64_t            frame_index = 0;
  common::Timestamp        timestamp{ 0 };
  estimator::UpdateStatus  status = estimator::UpdateStatus::kFailed;
  std::string              message;

  bool                     selected_keyframe = false;
  KeyframeRule             keyframe_rule = KeyframeRule::kNone;
  bool                     epoch_committed = false;
  std::uint64_t            keyframe_epoch = 0;
  std::uint32_t            segment_id = 0;
  CandidateResetReason     reset_reason = CandidateResetReason::kNone;

  std::uint32_t            track_count = 0;
  std::uint32_t            observation_count = 0;
  std::uint32_t            disparity_count = 0;
  std::uint32_t            shared_count = 0;
  std::uint32_t            landmark_count = 0;
  std::uint32_t            culled_count = 0;
  std::uint32_t            dropped_track_count = 0;

  estimator::FusionMode    fusion_mode = estimator::FusionMode::kVisionOnly;
  std::optional<CandidateState> state;

  std::uint32_t            active_pose_count = 0;
  std::uint32_t            active_factor_count = 0;
  std::uint32_t            marginalized_pose_count = 0;
  std::uint32_t            retired_landmark_count = 0;
};
```

合同：

- `state` 当且仅当 `status == kOk`；`T_W_B` 必须 finite 且属于 SE(3)，其中 B 是
  adapter 规范化 IMU Body Frame；
- `velocity_W` / `bias_acc` 只有 candidate 实际拥有相应估计状态时才有值；gyro-only
  slice 不用伪造的零向量冒充 full inertial state；
- KF epoch 只在 `selected_keyframe && status == kOk` 时 commit；reject/fail 不推进；
- `track_count` 是 candidate tracker 本帧输出，不是 production track 数；
- fixed-lag slot missing、timestamp orphan 或 rollback 失败不写成“正常的非零计数”，而是
  `kEstimatorInvariant` terminal error；
- active pose/factor count 用于证明窗口有界，marginalized/retired count 用于证明生命周期
  实际推进；前两者是本帧提交后的存量，后两者是本帧增量；不公开 factor keys、slots、
  landmark values 或完整 track IDs；
- diagnostics 不负责文件 I/O。composition root 在 `finish()` 后写 candidate artifact，
  I/O failure 仍是 session/bench error，不污染 VIO state transaction。

### 8.4 finish 合同

```cpp
struct CandidateRunResult
{
  std::optional<common::Trajectory> trajectory;
  std::optional<common::Trajectory> keyframe_trajectory;
  std::vector<CandidateFrameDiagnostics> diagnostics;
  CandidateCounts counts;
  std::optional<CandidateError> error;
};
```

- 无 terminal error 时返回 candidate accepted states 构成的 trajectory；其中存在
  frame-level `kFailed` 仍完整报告，但 bench 不得让该 run 进入精度通过结论；
- terminal error 时保留错误前 diagnostics/counts 供定位，两个 trajectory 均为空；
- 每个实际调用并进入 candidate 的 input 恰好一行 diagnostics，含 terminal failure 行；
- `finish() &&` 交叉校验 diagnostics、counts、accepted poses、KF commits 与 timestamps；
  不一致转 `kTrajectoryInvariant`。

## 9. 测试与验收候选（待确认）

### 9.1 为什么先做 seam tracer

P1 已证明 optimizer lifecycle 能运行，但没证明 whole-pipeline candidate ownership 正确。
若第一步直接接 fixed-lag，第一次 trajectory 分叉会同时混入两类未知量：

- candidate tracker/KF/cull/drop 是否真的与 production 隔离；
- fixed-lag graph/marginal prior 是否改变状态。

因此推荐分两个可删除临时代码的 vertical slice：P2a 先用第二套现行 concrete batch
estimator 验证 seam，P2b 再把 candidate PIMPL 内的临时 batch implementation **替换**为
唯一 concrete fixed-lag implementation。P2b 不保留 backend enum、recipe、factory 或
compatibility path。

P2a 是 ownership probe，不产生精度晋级结论；P2b 才能生成进入 VIO-vs-VO 门的有效
candidate trajectory。

### 9.2 TDD RED → GREEN 顺序

所有测试只穿过已确认的 `CandidatePipeline::create/process/finish` public seam，使用真实
`StereoTracker`、`KeyframeEpochGate` 与 concrete estimator，不 mock 本仓库 module：

1. **RED ①：完整最小闭环。** 用 `tests/frontend/synthetic_stereo.hpp` 的已知静态双目点阵、
   sync 首帧零段和合法静止 IMU 区间，要求 candidate 接受已知 bootstrap state，返回有限
   identity-gauge `T_W_B`，`finish()` 产生非空、严格单调 trajectory；输入 image/IMU bytes
   调用前后不变。
2. **GREEN ①：最小 PIMPL。** 只实现 input validation、candidate-owned tracker/gate/
   batch estimator、trajectory；不提前实现 perturbation、writer 或 fixed-lag switch。
3. **RED/GREEN ②：独立实例。** 两个 candidate 实例消费同一 synthetic 序列，完整
   diagnostics/trajectory 相同；只改变其中一个实例的一帧输入后允许其递归分叉，另一实例
   仍与未扰动 reference 完全相同。
4. **RED/GREEN ③：错误合同。** 逆序 timestamp、`t_prev` 不匹配、非法非-gap IMU 端点
   产生 typed terminal error、保留失败行且不返回 trajectory；可 rollback 的 estimator
   `kFailed` 记录后仍可处理下一帧。
5. **RED/GREEN ④：session isolation。** candidate disabled/enabled 时 production
   `est.tum`、`kf.tum`、`diag.csv` 与 config hash 不变；candidate failure 只停止 candidate，
   production 继续到 EOS。
6. **RED/GREEN ⑤：artifact/analyzer。** composition root 写独立 candidate trajectory、KF
   trajectory 与 strict diagnostics；schema/order/numeric/count/ownership 错误显式失败。

每个编号按“一条失败测试 → 最小实现 → 下一条测试”推进，不先横向写完全部测试。

### 9.3 P2a synthetic 与 MH_01 seam 门

P2a candidate 暂时使用与 production 相同的 concrete batch implementation。通过条件：

1. 定向 candidate tests、apps integration tests、完整 unit 全部通过；
2. synthetic twin 在相同 input 下 status、KF selected/commit/epoch、state、cull/drop counts、
   diagnostics 与 trajectory 相同；candidate-only perturbation 不改变 control instance；
3. MH_01 candidate 开关打开后，production `est.tum`、`kf.tum`、`diag.csv` 与 B3 reference
   逐字节相同，config hash 仍为 `f6808356`；
4. MH_01 candidate trajectory/KF trajectory 与同 run production 逐字节相同；映射后的
   frame status、KF transaction、`T_W_B`、bias、segment、cull/drop 字段逐行相同；
5. candidate diagnostics 行数等于送入 candidate 的 frame 数，terminal error=`0`，
   `failed=0`，无 production state fallback；
6. artifact 显式记录 `ownership=full_pipeline`；candidate wall time 单独报告，不污染
   production frontend/estimator stage timing。

任一条件失败，先修 seam/ownership，不接 fixed-lag。全部通过后记录 P2a 结果，并在 P2b
删除临时 batch candidate code。

### 9.4 P2b fixed-lag structural gate

P2b 用唯一 concrete fixed-lag estimator 替换 candidate PIMPL 内 batch estimator。先用
synthetic sequence 锁定：

- active pose/state 数始终有界，cutoff 严格 `<` 的既有 P0 合同保持；
- factor slot、variable timestamp、landmark generation/retirement 与 marginal prior 由
  candidate 自己拥有；
- slot missing、timestamp orphan、rollback failure、non-finite state 均是 terminal error；
- accepted-KF schedule、PIM interval、cull/drop 与 reset 全部来自 candidate feedback，
  不读取 production graph events 或 initial values；
- candidate enabled/failed 都不改变 production 三主产物。

通过 synthetic structural gate 后只跑一次 MH_01，不先扫 lag、threshold、bias 或 cull
knob。结构门：terminal error=`0`、failed=`0`、finite、completion/coverage 不低于 paired
VO、无未声明 reset、active state/factor 有界。

### 9.5 精度出口

精度门沿用 `docs/roadmap.md`，不因 fixed-lag 改口径：

1. **MH_01 首门**：candidate 与同代码 `--no-imu` VO 在 exact-common support 上，
   translation ATE RMSE 与 1 s translation RPE RMSE 都严格 `candidate < VO`；同时 health
   gate 通过。B3 的 MH_01 `0.083321/0.016899 m` 与 paired VO
   `0.080964/0.017781 m` 只作当前诊断锚，不能把 RPE 单项通过写成总门通过。
2. **失败停止**：MH_01 任一指标或健康门失败，停在 MH_01，先按 candidate diagnostics
   定位首个分叉/坏桶；不靠扫参、放宽 common support 或平均值掩盖。
3. **sentinel**：MH_01 双指标严格通过后才跑 MH_05；同样逐序列 paired exact-common
   双指标与健康门。
4. **EuRoC 11/11**：每条序列都必须同时严格优于各自 VO 并通过健康门；任何一条失败，
   M4/M4.4 仍未完成，不以均值或通过数替代。
5. **IMU-off gate**：清理 candidate 试验代码后的 `--no-imu` 主产物继续与冻结 VO
   reference 逐字节相同。

P2a 通过只授权 P2b；P2b 通过 MH_01/MH_05 也不等于 11/11 完成。只有上述完整出口有
当前态证据时，才能把 M4/M4.4 标为完成。

TDD seam、错误合同与 P2a→P2b 验收分片均已按默认推荐项固定。P2a 从第一条 public-seam
RED test 开始；本设计不授权跳过 P2a 直接 handoff fixed-lag。
