## 1. 问题、术语与证据边界

本次不重复调研 IMU 旋转方向、外参共轭或 pixel threshold；这些内容见既有
[Rule 4 调研](m4.4-rule4-imu-rotation-reference.md)。本次只回答 successor B 的
五个问题：

1. 成熟 VIO/SLAM 是否把 motion/quality **evidence** 与 keyframe
   **schedule/admission policy** 分开；
2. 是否使用 hard minimum interval、soft cooldown、最大间隔、安全规则 bypass、
   连续确认或 hysteresis；
3. 如何处理“本帧看起来需要 KF”与“后端当前能否接纳 KF”的区别；
4. 是否通过不依赖 last accepted KF 的 evidence baseline，降低一次选择改变后
   继续级联的敏感性；
5. 是否存在冻结旧 schedule、shadow decision 或 real-dataset trace conformance
   一类迁移门。

本文采用以下术语：

- **evidence**：当前输入上可观测的 motion/quality 数值，例如 disparity、track
  overlap、inlier count、时间间隔和 mapper queue 状态；
- **policy**：规则优先级、阈值、cooldown、max-gap 与 bypass 的组合；
- **candidate**：policy 认为应该成为 KF 的帧；
- **admission**：系统是否实际把 candidate 接入 KF/map/window 路径；
- **accepted schedule**：实际接纳的 KF 时间戳序列，而不是候选数或平均间隔。

## 2. 结论摘要

### 2.1 上游事实

1. **没有统一的“纯 EvidenceBuilder + 纯 Scheduler”行业接口。** Kimera-VIO 和
   OKVIS2-X 都有相对集中的 keyframe decision 函数，但函数内部仍同时计算
   evidence 与应用 policy；VINS-Fusion、Basalt 和 ORB-SLAM3 更直接地把规则写在
   estimator/tracking 流程中。模块边界是否拆开仍是本仓库的工程设计，不应写成
   “上游都这样做”。
2. **时间规则通常不是一个无条件 cooldown。** 本次范围内只有 Basalt 在正常
   steady-state evidence 路径上有直接的 hard minimum frame gap；ORB-SLAM3 在 IMU
   初始化期使用 `0.25 s` 固定节拍（不足时禁止、到时强制），但初始化后的 minimum
   frame gap 是 0。Kimera 的 minimum time 只门控普通 disparity 状态翻转，max
   disparity、低 feature 数、max time 和 user force 均可绕过；ORB-SLAM3 初始化后
   的 inertial `0.5 s` 是最大间隔触发，不是最小间隔。
3. **没有找到 keyframe selector 使用“两次连续越阈才接纳”的实现。** 被核对的
   selector 都是当前帧直接判定。Kimera 有一个“low disparity 首次出现”的一位状态
   翻转，但没有两套 enter/exit threshold，也不累计连续命中次数；不能把它称为
   conventional hysteresis 或 two-hit confirmation。
4. **ORB-SLAM3 明确区分了 need evidence 与 downstream admission。** 它先形成
   `c1a/c1b/c1c/c2/c3/c4`，随后根据 Local Mapping 是否 idle、队列长度与 sensor
   类型决定是否真正插入；必要时还会请求中断 BA。DSO 在异步 tracking/mapping
   之间也把布尔 need 压成一个 reference-ID watermark，但这是吞吐/backpressure
   机制，不是精度迁移门。
5. **没有找到真正切断 accepted-schedule baseline 级联的上游 selector。**
   VINS-Fusion 表面比较 `frame_count-2/-1`，但这是会被 marginalization 重排的滑窗
   slot，不是固定相邻输入时间戳；一次 `MARGIN_SECOND_NEW` 后，旧 slot 保留、当前
   frame 覆盖第二新 slot，下一次比较区间随 prior schedule 延长。OKVIS2-X 使用当前
   coverage 与 map-wide keyframe overlap，而不是只绑定 last KF；它降低单锚敏感性，
   但仍依赖已接纳 map，因此也没有消除反馈。
6. **在这些固定 revision 中没有找到 real-dataset 冻结旧 schedule、shadow
   selector 或旧/新 policy conformance migration gate。** 最接近的是 Kimera 的
   synthetic sequence test：它逐帧断言 KF/non-KF 结果，用来锁规则语义；它不是
   对旧实现的 dataset trace 回放，也不要求新策略复现旧 schedule。
7. **这些上游都没有 phad-vio 当前的 candidate 被 estimator 拒绝后再决定是否推进
   baseline 的合同。** Kimera 在 frontend 内立即推进 last-KF；ORB-SLAM3 在送入
   Local Mapping 后推进 last-KF；OKVIS2-X 先把 state 加入 estimator，再设置
   keyframe flag。因而 `candidate -> update -> accepted/rejected -> commit` 的事务语义
   必须由本仓库根据 `kOk/kRejected/kFailed` 自行设计和验证。

### 2.2 对 successor B 的边界结论

可迁移的是**模式族**：显式 evidence、规则 reason、hard/soft timing gate、max-gap
安全阀、force/veto 分类、downstream admission 状态，以及 map-wide evidence 等
降低单锚敏感性的思路。不可直接迁移的是具体阈值、bypass 集合、连续确认次数、
固定 adjacent-input baseline、允许的 schedule divergence、失败事务和冻结 control
trace 门；这些只能做本仓库 A/B。

## 3. VINS-Fusion：滑窗 slot evidence 与 marginalization 形成反馈

### 3.1 slot index 不等于固定输入 timestamp

`addFeatureCheckParallax()` 在加入当前图像 observations 后，先计算 track/new/long
feature 数；初始化、track 少、long track 少或新 feature 比例过高时直接返回
keyframe。否则它只比较 `frame_count-2` 与 `frame_count-1` 的公共 tracks。见
[`feature_manager.cpp:52-118`](https://github.com/HKUST-Aerial-Robotics/VINS-Fusion/blob/be55a937a57436548ddfb1bd324bc1e9a9e828e0/vins_estimator/src/estimator/feature_manager.cpp#L52-L118)
与
[`feature_manager.cpp:530-562`](https://github.com/HKUST-Aerial-Robotics/VINS-Fusion/blob/be55a937a57436548ddfb1bd324bc1e9a9e828e0/vins_estimator/src/estimator/feature_manager.cpp#L530-L562)。

所以它决定的是“当前帧到达后，第二新 slot 是否保留为 KF”。在窗口尚未发生
`MARGIN_SECOND_NEW` collapse 时，这两个 slot 可以对应相邻输入帧；但 slot index
不是不可变的原始 timestamp identity。

### 3.2 evidence 与 policy 仍未形成独立接口

返回的单一 `bool` 立即映射为：

- `true -> MARGIN_OLD`，第二新帧保留为 KF；
- `false -> MARGIN_SECOND_NEW`，第二新帧作为 non-KF 丢弃。

见
[`estimator.cpp:411-434`](https://github.com/HKUST-Aerial-Robotics/VINS-Fusion/blob/be55a937a57436548ddfb1bd324bc1e9a9e828e0/vins_estimator/src/estimator/estimator.cpp#L411-L434)。
窗口满且选择 non-KF 时，当前 state 覆盖第二新 state，IMU 段合并，并调用
`removeFront()` 删除对应视觉 observation；见
[`estimator.cpp:1329-1428`](https://github.com/HKUST-Aerial-Robotics/VINS-Fusion/blob/be55a937a57436548ddfb1bd324bc1e9a9e828e0/vins_estimator/src/estimator/estimator.cpp#L1329-L1428)
与
[`feature_manager.cpp:508-527`](https://github.com/HKUST-Aerial-Robotics/VINS-Fusion/blob/be55a937a57436548ddfb1bd324bc1e9a9e828e0/vins_estimator/src/estimator/feature_manager.cpp#L508-L527)。

这段覆盖语义意味着：一次 non-KF 后，`frame_count-2` 保留，先前 current frame
进入 `frame_count-1`；下一图像到达时仍比较这两个 slot。连续 non-KF 会让真实
timestamp baseline 从保留 state 累积到新 candidate，prior marginalization decision
因而会改变下一次 evidence 区间。

**事实边界**：VINS-Fusion 没有提供 schedule-independent motion baseline，也没有
独立 scheduler、minimum/maximum interval、连续确认或 downstream reject/commit。
真正固定 adjacent-input timestamp 的 evidence 仍只能作为本仓库 A/B；它会改变
Rule 4 的物理语义和 seed/window 交互，不能称为 VINS 等价迁移。

## 4. Kimera-VIO：集中 decision、soft minimum、max-gap 与状态翻转

### 4.1 同一函数里显式列出 evidence 与 policy

`shouldBeKeyframe(frame, frame_lkf)` 先计算：

- 距 last KF 的 min/max time；
- valid feature 数；
- last-KF→current raw median disparity；
- 当前 disparity 是 low/enough，以及上一个 KF tracking status 是否已经 low。

随后一次性组合：

```text
max_time
OR max_disparity
OR ((enough_disparity OR low_disparity_first_time) AND min_time)
OR low_feature_count
OR user_forced
```

源码见
[`VisionImuFrontend.cpp:175-231`](https://github.com/MIT-SPARK/Kimera-VIO/blob/ce8c59b7b273ab5ac29db7e5572e1623760e19c7/src/frontend/VisionImuFrontend.cpp#L175-L231)。
这是“计算步骤清楚”的参考，但 evidence 与 policy 仍在同一个函数，并非两个可单测
接口。

### 4.2 minimum 不是 hard cooldown；状态翻转不是连续确认

`min_intra_keyframe_time` 只出现在 `disparity_flipped` 中。以下规则不受其限制：

- `max_disparity_since_lkf`；
- feature 数过低；
- `max_intra_keyframe_time`；
- `frame.isKeyframe_` 外部强制。

上游测试明确锁定这些行为：高于 max disparity 时即使 min time 未到仍是 KF；从
high disparity 转到 low disparity 的第一帧可成为 KF，下一 low-disparity 帧不是；
max time 到达后再次成为 KF。见
[`testStereoVisionImuFrontend.cpp:674-925`](https://github.com/MIT-SPARK/Kimera-VIO/blob/ce8c59b7b273ab5ac29db7e5572e1623760e19c7/tests/testStereoVisionImuFrontend.cpp#L674-L925)。

这里的记忆只有“上一 KF 是不是 low disparity”这一位分类，并使用同一个 disparity
threshold。它是 edge/state-transition trigger，不是“两帧连续越阈”，也不是带不同
enter/exit threshold 的 hysteresis。

EuRoC 配置是 min `0.2 s`、max `5.0 s`，`max_disparity_since_lkf=1000` 且注明
“large value to disable”；见
[`FrontendParams.yaml:64-73`](https://github.com/MIT-SPARK/Kimera-VIO/blob/ce8c59b7b273ab5ac29db7e5572e1623760e19c7/params/Euroc/FrontendParams.yaml#L64-L73)。
因此不能把 max-disparity bypass 当成 EuRoC 已启用、已验证的主路径。

### 4.3 selector 接纳后立即推进 baseline

一旦 `shouldBeKeyframe()` 返回 true，frontend 运行 RANSAC/stereo、设置 KF flag 和
`last_keyframe_timestamp_`，并把 `stereoFrame_lkf_` 直接更新为当前帧；见
[`StereoVisionImuFrontend.cpp:339-448`](https://github.com/MIT-SPARK/Kimera-VIO/blob/ce8c59b7b273ab5ac29db7e5572e1623760e19c7/src/frontend/StereoVisionImuFrontend.cpp#L339-L448)。
随后下一次 spin 才把该 KF/PIM 输出给 backend；见
[`StereoVisionImuFrontend.cpp:174-220`](https://github.com/MIT-SPARK/Kimera-VIO/blob/ce8c59b7b273ab5ac29db7e5572e1623760e19c7/src/frontend/StereoVisionImuFrontend.cpp#L174-L220)。

因此 Kimera 的 last-KF baseline 会随 schedule 自反馈，但它没有 phad-vio 式 backend
`kFailed` 后回滚 selector baseline 的问题。不能拿它证明“candidate 时推进”适合本
仓库。

## 5. ORB-SLAM3：need evidence 与 Local Mapping admission 的直接证据

### 5.1 safety block、motion/quality evidence 与时间规则

`NeedNewKeyFrame()` 先处理 IMU 初始化阶段：距 last KF 达 `0.25 s` 才插入；这使
初始化 KF 间隔不会短于约 `0.25 s`，但代码语义是“时间一到就插”的周期/max-gap
规则，不是 evidence 越阈后的 cooldown。随后它依次阻止 only-tracking、Local
Mapping stopped/stop-requested，以及 relocalization 后过早插入；见
[`Tracking.cc:3064-3094`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc#L3064-L3094)。

正常路径把条件显式命名为：

- `c1a`：超过最大帧数；
- `c1b`：超过最小帧数且 Local Mapping idle；
- `c1c`：特定非惯性 stereo/RGB-D 的弱跟踪；
- `c2`：相对 reference KF 的 map matches 少，但仍有至少 15 inliers；
- `c3`：inertial 模式距 last KF 达 `0.5 s`；
- `c4`：IMU monocular 中低 inlier 或 recently-lost。

见
[`Tracking.cc:3096-3188`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc#L3096-L3188)。
固定 revision 的 `mMinFrames=0`、`mMaxFrames=fps`，见
[`Tracking.cc:579-585`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc#L579-L585)
和
[`Tracking.cc:1152-1158`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc#L1152-L1158)。
所以初始化完成后的 inertial 主路径没有 nonzero frame cooldown；`c3=0.5 s` 是
最大间隔安全阀。

### 5.2 admission 会参考 mapper capacity

即使 need 条件成立，系统仍区分：

- Local Mapping idle/initializing：接纳；
- busy：先 `InterruptBA()`；
- stereo/RGB-D 且 queue `<3`：仍接纳；
- queue 已满或 monocular mapper busy：拒绝本次插入。

见
[`Tracking.cc:3187-3213`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc#L3187-L3213)。
Local Mapping 在处理期间切换 `AcceptKeyFrames`，接口与实现见
[`LocalMapping.h:54-79`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/include/LocalMapping.h#L54-L79)
和
[`LocalMapping.cc:873-904`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/LocalMapping.cc#L873-L904)。

这是本次范围内最明确的 need/admission 分离。不过它们仍写在一个有副作用的函数中
（会中断 BA），并且一旦创建 KF，就送入 Local Mapping 并立即更新
`mnLastKeyFrameId/mpLastKeyFrame`；见
[`Tracking.cc:3334-3341`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/4452a3c4ab75b1cde34e5505a36ec3f9edcdc4c4/src/Tracking.cc#L3334-L3341)。
因此可迁移的是“need reason 与 admission reason 分开记录”的模式，不是其线程副作用
或阈值。

## 6. Basalt：connection evidence AND hard minimum frame gap

Basalt estimator 构造时把 `take_kf=true`，因此首帧绕过普通规则；同时
`frames_after_kf=0`。见
[`sqrt_keypoint_vio.cpp:59-71`](https://gitlab.com/VladyslavUsenko/basalt/-/blob/0f3b2b52c807f70ff4e2973ce253c73329eea7bc/src/vi_estimator/sqrt_keypoint_vio.cpp#L59-71)。

后续 KF 条件只有一个 AND 组合：camera 0 中已连接 landmark 的比例低于
`vio_new_kf_keypoints_thresh`，且
`frames_after_kf > vio_min_frames_after_kf`。接纳后 counter 清零，否则每帧加一；
见
[`sqrt_keypoint_vio.cpp:336-384`](https://gitlab.com/VladyslavUsenko/basalt/-/blob/0f3b2b52c807f70ff4e2973ce253c73329eea7bc/src/vi_estimator/sqrt_keypoint_vio.cpp#L336-384)
和
[`sqrt_keypoint_vio.cpp:465-468`](https://gitlab.com/VladyslavUsenko/basalt/-/blob/0f3b2b52c807f70ff4e2973ce253c73329eea7bc/src/vi_estimator/sqrt_keypoint_vio.cpp#L465-L468)。
默认 `min=5`、connection ratio `0.7`，见
[`vio_config.cpp:58-65`](https://gitlab.com/VladyslavUsenko/basalt/-/blob/0f3b2b52c807f70ff4e2973ce253c73329eea7bc/src/utils/vio_config.cpp#L58-65)。

这是 hard cooldown 的直接证据：所有普通 connection-triggered KF 都必须等待，
没有 max-gap 或低质量 bypass。严格 `>5` 表示已经经过 6 个 non-KF 帧；参数值和
bypass 语义都与其 7 KF + 3 state 窗口及 landmark hosting 共生，不能直接外推到
phad-vio。

Basalt evidence 不是简单 last-KF pixel difference，但 connection ratio 取决于哪些
landmark 已由历史 KF hosted/seeded；所以 accepted schedule 仍通过 map 内容反馈到
下一次 evidence，并未冻结 schedule。

## 7. OKVIS2-X：视觉 overlap 函数 + 外部 force prior

### 7.1 相对清楚的接口 seam

`dataAssociationAndInitialization()` 先完成 map matching、motion stereo 与 tracking
quality，再决定 KF。外部 `kfPrior` 为 true 时直接强制；否则调用
`doWeNeedANewKeyframe(estimator, currentFrame)`；首帧强制。见
[`Frontend.cpp:673-788`](https://github.com/ethz-mrl/OKVIS2-X/blob/38043e4afe56d9b32a98434cc74e723737dd2bce/okvis_frontend/src/Frontend.cpp#L673-L788)。
其公开 frontend interface 也把 `kfPrior` 和输出 `asKeyframe` 明确列为参数，见
[`ViFrontendInterface.hpp:76-88`](https://github.com/ethz-mrl/OKVIS2-X/blob/38043e4afe56d9b32a98434cc74e723737dd2bce/okvis_common/include/okvis/ViFrontendInterface.hpp#L76-L88)。

这提供了“sensor-specific force evidence 从 caller 输入，视觉 selector 不必认识
LiDAR”的窄 seam，但仍只是一个 `bool`，没有 reason、置信度或通用 evidence object。

### 7.2 map-wide overlap 降低单 last-KF 敏感性

`doWeNeedANewKeyframe()`：

- estimator 中少于 4 帧时强制 KF；
- frontend 尚未 initialized 时禁止 KF；
- 计算当前 detections 与已匹配 landmarks 的 coverage IoU；
- 再与所有 keyframe/loop-closure/IMU-window KF 的共同 landmark coverage 比较；
- detection 太少时禁止把坏帧作为 KF；否则 overlap 不高于阈值时接纳。

见
[`Frontend.cpp:1172-1281`](https://github.com/ethz-mrl/OKVIS2-X/blob/38043e4afe56d9b32a98434cc74e723737dd2bce/okvis_frontend/src/Frontend.cpp#L1172-L1281)。
EuRoC 配置阈值为 `0.60`，见
[`config/euroc/okvis2.yaml:70-79`](https://github.com/ethz-mrl/OKVIS2-X/blob/38043e4afe56d9b32a98434cc74e723737dd2bce/config/euroc/okvis2.yaml#L70-L79)。

这不是 last accepted KF 单锚 evidence；但“所有已有 KF/landmark”本身仍由历史
schedule 决定，因此只是分散敏感性，不是因果解耦。它也没有 minimum interval、
maximum interval、连续确认或 hysteresis。

### 7.3 没有 candidate reject transaction

composition root 先以 `asKeyframe=false` 把 state 加到 estimator，再调用 frontend
决定，之后用 `setKeyframe()` 改 flag；初始化匹配失败则清空 frontend 和整个
estimator。见
[`ThreadedSlam.cpp:737-839`](https://github.com/ethz-mrl/OKVIS2-X/blob/38043e4afe56d9b32a98434cc74e723737dd2bce/okvis_multisensor_processing/src/ThreadedSlam.cpp#L737-L839)。
这不是“候选交给 estimator 后，按单帧 kOk/kFailed 事务提交 baseline”的参考。

## 8. DSO 补充：异步 need watermark，不是 schedule conformance

DSO 不是 VIO，但它展示了 tracking evidence 与异步 mapping admission 的另一种
成熟处理。tracking thread 用 translation/rotation/combined flow、affine brightness
变化和 coarse RMSE 组成 `needToMakeKF`；也可选择固定目标 KF rate。见
[`FullSystem.cpp:851-900`](https://github.com/JakobEngel/dso/blob/7b0c99f01d238f801c625beaff90240bcb007198/src/FullSystem/FullSystem.cpp#L851-L900)
与
[`settings.cpp:35-42`](https://github.com/JakobEngel/dso/blob/7b0c99f01d238f801c625beaff90240bcb007198/src/util/settings.cpp#L35-L42)。

在线程化路径中，`needKF` 不绑定“必须接纳当前帧”；它把当前 tracking reference ID
写入 `needNewKFAfter`。mapping loop 首两帧强制 KF；积压时先把帧作为 non-KF 或
丢弃，队列清空后再根据 watermark 选择一个可处理帧成为 KF。见
[`FullSystem.cpp:904-1011`](https://github.com/JakobEngel/dso/blob/7b0c99f01d238f801c625beaff90240bcb007198/src/FullSystem/FullSystem.cpp#L904-L1011)
及 watermark 合同
[`FullSystem.h:307-315`](https://github.com/JakobEngel/dso/blob/7b0c99f01d238f801c625beaff90240bcb007198/src/FullSystem/FullSystem.h#L307-L315)。

这能合并重复 need、限制 mapping backlog，但可能接纳比触发帧更晚的帧；目标是实时
吞吐而不是复现旧 schedule。因此只能借鉴“need 与 admission identity 不必混为一谈”
这一概念，不能把 watermark 直接移植为 M4.4 精度 guard。

## 9. 行为矩阵

| 系统 | evidence/policy seam | minimum interval | maximum interval | safety force/veto | 连续确认 / hysteresis | admission 反馈 | evidence baseline |
|---|---|---|---|---|---|---|---|
| VINS-Fusion | 一个 `bool` 函数，内部仍混合 | 无 | 无 | 初始化/track 少等 force | 无 | 无 reject | 保留 slot→candidate；**随 schedule 改变** |
| Kimera-VIO | 集中 `shouldBeKeyframe()`，内部混合 | soft；只门控普通 disparity transition | 有；max time | max disparity、低 features、user force 绕过 | 一位 low/enough 状态翻转；**非**连续确认/双阈值 hysteresis | 无 reject | last KF |
| ORB-SLAM3 | 同一函数先 evidence、后 mapper admission | IMU 初始化期约 0.25 s；初始化后 `mMinFrames=0` | inertial 0.5 s、frame max | stopped/relocalization veto；weak/recently-lost force | 无 | **mapper idle/queue/BA** | last/reference KF |
| Basalt | estimator flow 内联 | **hard `frames_after_kf > 5`** | 无 | 首帧 bypass；普通路径无 bypass | 无 | 无 reject | 当前 map connection |
| OKVIS2-X | frontend decision 函数 + external `kfPrior` | 无 | 无 | first frames / external force；uninitialized/低 detections veto | 无 | 无单帧 reject | map-wide overlap |
| DSO | tracking need + async mapping watermark | 无；可改固定 KF rate | composite motion/RMSE 触发 | 首两帧 force；lost 为错误路径 | 无 | **mapping backlog** | tracking reference |

表中的“无”只表示本次固定 revision 的 keyframe selector 没有该机制，不证明其它

## 10. accepted-KF baseline 级联：上游实际怎么处理

### 10.1 大多数系统接受闭环反馈，而不是消除它

典型反馈是：

```text
accepted KF_t
  -> last-KF / map / window / hosted landmarks 改变
  -> frame_(t+1) evidence 改变
  -> accepted KF_(t+1) 改变
```

Kimera、ORB-SLAM3 和 DSO 显式使用 last/reference KF；Basalt、OKVIS2-X 虽不只比较
last KF，evidence 仍依赖由历史 KF 构成的 map。它们把这种反馈当算法本身，没有为
替换某个 evidence source 增加 schedule divergence budget。

### 10.2 三种受限结构都没有切断反馈

1. **延迟决定第二新 slot（VINS-Fusion）**：把当前图像处理与被标记 frame identity
   错开一帧，但 slot collapse 仍让下一 baseline 随 schedule 改变；
2. **map-wide evidence（OKVIS2-X）**：避免单 last-KF 锚主导，但没有消除历史 map
   反馈；
3. **need/admission 分开（ORB-SLAM3、DSO）**：把下游容量或异步吞吐从 motion
   evidence 中显式拿出来，但 accepted schedule 仍可改变。

这些模式都没有保证新 evidence source 与旧 source 产生相同 schedule。

### 10.3 conformance 类证据的真实边界

Kimera 的 synthetic `testDisparityCheck` 是本次唯一直接找到的逐帧 schedule
断言：同一测试序列依次期望 KF/KF/KF/KF/KF/non-KF/KF。它适合锁定规则边界和
bypass 语义。没有找到以下生产迁移机制：

- 在同一 dataset run 中 shadow 运行旧/新 selector；
- 用旧 selector 的 accepted timestamps 驱动新 evidence，冻结 estimator window；
- 对 real-dataset schedule 设置 first-divergence 或 timestamp-overlap gate；
- 新策略晋级前要求与旧策略逐帧 conformance。

因此“冻结 control schedule”若用于 phad-vio，应明确标记为**本地诊断 oracle**，
用于区分 evidence 数值问题与 live schedule feedback；它不是被上述上游验证过的
产品 policy，也不应永久保留 BA/IMU 双选择路径。

## 11. 可迁移模式与必须本仓库 A/B 的项目

| 候选模式 | 上游证据 | 对 phad-vio 的分类 | 限制 |
|---|---|---|---|
| 把 raw evidence、policy reason、admission reason 分别记录 | ORB-SLAM3 need vs mapper；Kimera/OKVIS 集中 decision | **可直接迁移的诊断/接口原则** | 上游没有统一类型，具体 API 仍需本地设计 |
| hard minimum frame gap | Basalt | **模式族可迁移** | `N=5`、严格 `>` 与规则 bypass 集必须本地 A/B |
| soft minimum + max-gap + safety bypass | Kimera、ORB-SLAM3 | **policy 形状可迁移** | 哪些规则绕过、max time 数值必须本地 A/B |
| downstream capacity 参与 admission | ORB-SLAM3、DSO | **概念可迁移** | phad 是 estimator outcome，不是 mapper queue；不能照抄线程副作用 |
| 延迟决定第二新 slot | VINS-Fusion | **有上游实现，但不能解决本次 baseline 级联** | slot collapse 后仍随 prior schedule 改变 |
| 真正固定 adjacent-input timestamp evidence | 未找到 | **仅本仓库可证伪 A/B** | 会改变 Rule 4 last-KF 物理语义和窗口/seed 交互 |
| map-wide overlap | OKVIS2-X | **未来候选，不是 M4.4 直接替换** | 需要不同 map/landmark coverage 合同，范围明显扩大 |
| low/enough 状态翻转 | Kimera | **可研究的状态机参考** | 不是 conventional hysteresis，不能宣传为 two-hit 证据 |
| 连续两次越阈才接纳 | 未找到 | **仅本仓库可证伪 A/B** | 必须先给出要抑制的噪声/抖动日志证据 |
| 两阈值 hysteresis | 未找到 | **仅本仓库可证伪 A/B** | 必须定义 enter/exit evidence 与状态 reset |
| 冻结旧 dataset schedule / divergence budget | 未找到；仅 Kimera synthetic sequence unit test 接近 | **只作本地迁移探针/门禁 A/B** | 不进入最终 production decision path |
| candidate 后按 `kOk/kRejected/kFailed` 提交 baseline | 上游无同构合同 | **本仓库必须设计并测试** | 必须与 estimator 真实 outcome 原子一致 |

## 12. successor B 可由一手资料支持的设计约束

以下是工程综合推论，不是任一上游的原样接口：

1. selector 的输出至少要能区分 `evidence`、`eligible`、`candidate reason`、
   `admission/commit outcome`；只返回 `bool` 会丢失本次失败归因所需的信息。
2. safety 规则必须显式分类为 force、veto 或普通 evidence；不能把所有规则放进一个
   cooldown 后再从结果猜哪些被抑制。Kimera 与 ORB-SLAM3 都把 bypass/block 写成
   独立条件。
3. max-gap 与 minimum gap 是两个方向相反的合同。Basalt 只能证明 hard minimum
   family，Kimera/ORB 才能证明 max-gap family；实现和诊断不能共用一个含糊字段。
4. 若要降低 accepted-KF baseline 级联，第一步应先用 probe 固定输入与 schedule，
   测出首次 evidence divergence；是否改成真正固定 adjacent-input timestamp 的
   evidence 必须作为语义变更单独 A/B，而不是藏在接口重构中。VINS 的 slot index
   不能作为“已经上游验证 schedule-independent”的依据。
5. estimator 会拒绝 candidate 是 phad-vio 的本地事实。accepted-KF baseline 只能在
   真实 accepted outcome 后推进；上游“selector true 即推进”不能覆盖这项合同。
6. 行为保持的 selector 抽取可用 exact synthetic schedule 和 MH_01 frozen control
   trace 双重验证；前者属于上游已有的 semantic-test 模式，后者明确是本仓库迁移
   保障，不应成为长期双产品路径。
7. 在日志没有显示单帧 evidence 在阈值附近反复翻转前，不应先引入 two-hit 或
   hysteresis。当前 M4.4 负结果已经证明 schedule 大幅改变，但尚未证明原因是阈值
   抖动。

## 13. 证据缺口与不能下的结论

1. 本次核对的是表列固定 revision，不证明其它 branch/fork 没有 consecutive
   confirmation、shadow selector 或 schedule replay。
2. “没有找到冻结 schedule 迁移门”是 scoped repository finding，不是对整个 SLAM
   工业界的不存在证明；闭源产品无法由本调研核对。
3. DSO 的 watermark 服务异步 mapping 吞吐，且 DSO 是 VO；它不能证明 VIO 精度
   会因延迟 admission 改善。
4. VINS-Fusion 的 `frame_count-2/-1` 是窗口 slot；non-KF collapse 后真实 timestamp
   pair 会随 schedule 改变。不能把源码变量名或注释中的 second/third-last 误读成
   永久固定的 adjacent-input baseline。
5. OKVIS2-X 当前 evidence 依赖 estimator/map-wide landmarks；函数边界集中不等于
   纯函数，也不等于低耦合接口已经由上游证明。
6. Basalt `5`、Kimera `0.2/5.0 s`、ORB `0.25/0.5 s` 都与各自相机率、window、map
   和初始化状态耦合，不能作为 phad-vio 默认值的精度证据。
7. 上游没有 phad-vio 的 `kFailed` 回滚合同，因此 successor B 的事务测试仍需本仓库
   自己建立；不能用“成熟项目没做”作为省略理由。

## 14. 调研结论

successor B 不应从“加一个两击阈值”起步。更有一手资料支撑的顺序是：

1. 先把现有 evidence、policy reason、admission outcome 做成可观测且行为保持的 seam；
2. 用 frozen control schedule 作为一次性诊断 oracle，定位首次 divergence，但不把
   旧 BA selector 保留为产品兼容路径；
3. 根据日志区分 interval-baseline cascade、threshold jitter 与 downstream admission
   三种机制；
4. 只有机制证据成立后，再分别 A/B input baseline、minimum/max-gap 或状态机；
5. 最终仍以 live accepted schedule 下 VIO 精度优于 VO 为晋级条件，而不是以
   schedule 与 control 相似本身作为目标。

## 15. B0 日志后的收窄结论

2026-08-09，B0 `KeyframeEpochGate` 已通过 MH_01 三文件逐字节门，production
accepted schedule 相对 control 为 exact `518/518`。这补上了第 12.6 节要求的本地
行为保持 seam，但没有产生新的 guard 精度证据。

结合 B0 日志重新核对上述上游模式后，下一 probe 采用以下边界：

1. Kimera 的 synthetic 逐帧期望可支持“每帧记录并锁定 decision/result”的测试
   形状，不能支持运行时 shadow selector 会改善精度的结论；
2. ORB-SLAM3/DSO 的 need-admission 分离只支持把 reason 与 outcome 分开记录，不能
   把 mapper backpressure 搬成 phad 的 schedule guard；
3. Basalt hard gap 只作为离线计数的候选模式族；`N=5` 仍不进入 production；
4. 因而本仓库下一刀应是 CLI-only sidecar：production `decide/resolve` 完全不变，
   IMU evidence 只在同一 production accepted epoch 上计算并落盘；
5. sidecar 中的 threshold/cooldown/two-hit 结果只能称为 frozen-baseline
   first-order counterfactual，不能称为真实 accepted schedule，因为 estimator 并未
   按 shadow candidate 重跑。

这是基于 B0 本地证据与固定 revision 源码的工程推断，不是某个上游的原样实现。
