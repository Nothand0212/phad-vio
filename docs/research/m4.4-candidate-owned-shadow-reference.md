# M4.4 candidate-owned closed-loop shadow 一手资料对照

> 日期：2026-08-10
>
> 状态：P2 seam 决策输入；不代表 P2 已实现或已通过精度验收。
>
> 范围：只回答 alternative estimator 何时构成可解释的 closed-loop candidate；不讨论具体调参。

## 结论先行

**事实**：固定 lag optimizer 只封装数值图状态，不封装 VIO 系统的测量生成、关键帧选择、landmark 生命周期或前端反馈。GTSAM 的 fixed-lag API 要求调用方提交 factors、initial values、timestamps 和 removals；smoother 自己维护 estimate、linearization、factor slots、timestamp registry 与 marginal prior。

**推断**：因此，仅把 production 每轮已经决定好的 graph events 和初值送进另一 optimizer，得到的是“相同事件条件下的 optimizer branch”，不是“若 production 改用候选估计器会发生什么”的系统 counterfactual。

**建议**：若 P2 的输出要作为候选 production trajectory 计算 ATE、判断 VIO 是否优于 VO，最小正确 seam 应放在 rectified stereo frame / IMU packet 之后。production 与 candidate 只共享不可变传感器输入、标定和配置；candidate 自己拥有 tracker、keyframe gate、estimator、landmark/cull policy、graph/marginalization state 与 trajectory。若只在 `FrameTracks` 后分叉，必须标为 **track-conditioned backend shadow**，不可当 production counterfactual。

## 一手证据如何约束 ownership

### 1. GTSAM：optimizer state 必须独立，但远不足以构成系统 candidate

**事实**：GTSAM example 的调用方创建 `newFactors/newValues/newTimestamps`，并用上一轮 smoother estimate 递推下一姿态初值；`IncrementalFixedLagSmoother` 自己维护 ISAM2、timestamps、factor index 与 estimate。边缘化会把被移除变量的影响留在线性 prior 中，并依赖既有 linearization point。

**推断**：candidate 必须独立拥有 factor insertion/removal ledger、变量初值递推、relinearization/delta、timestamp/factor-slot registry 和 marginal prior。复制 production 当前 pose 后再共用 production graph events，会把 production 的历史决策和线性化历史注入 candidate。

### 2. Kimera-VIO 与 OKVIS：bias/map/pose 会反馈到下一轮前端

**事实**：Kimera pipeline 把 backend bias 和 landmark map 回传 frontend；backend 又用自己的 pose/velocity/bias 做 IMU prediction，并维护 smart-factor slots。OKVIS 从上一优化状态和 bias 做 IMU propagation，把 candidate pose 交给 data association/landmark initialization，优化后再取 pose/speed/bias 作为下一轮 seed。

**推断**：当 tracking、PnP、association 或 IMU propagation 消费 estimator 输出时，tracker state、map view、bias seed 与 keyframe schedule 都是内生变量。candidate 若消费 production 的这些反馈，只能解释为“固定 production feedback 下的局部替换”。

### 3. Basalt：可共享 measurement packet，但不能共享 estimator 历史

**事实**：所引 revision 中 optical-flow result 通过单向 queue 进入 estimator；每个 square-root VIO 实例仍自己保存 pose/velocity/bias、frame poses、landmark DB、keyframe flags、IMU history、previous optical-flow history 与 marginal prior。关键帧、triangulation、lost-landmark 和 marginalization 都根据这些本地状态决定。

**推断**：若上游确实不接收 estimator feedback，不可变 optical-flow packet 可以作为条件输入共享；但 candidate 仍须拥有 packet consumption history、keyframe/admission/cull 与 prior。这个例外不能外推到有 backend→frontend feedback 的系统。

### 4. OpenVINS 与 ORB-SLAM3：filter/map lifecycle 同样属于 candidate

**事实**：OpenVINS manager 同时拥有 filter state/covariance/clones、tracker/feature database 与 updater，并在 update 后删除 feature measurements、改 anchor、marginalize clone。ORB-SLAM3 的 tracking state包含 current/last frame、motion model、IMU bias、local map；keyframe decision读取 map/tracking state，LocalMapping 会 cull/fuse points 和 cull keyframes，optimizer 会写回 pose/velocity/bias并删除 outlier observations。

**推断**：无论 graph smoother 还是 EKF/filter，candidate ownership 都不止 pose。covariance/FEJ 或 linearized prior、clone/window、feature consumption/deletion、map/KF lifecycle 都会改变未来观测和约束，必须随 candidate 分叉。

## Candidate 必须独立拥有的状态与事件

| 类别 | candidate ownership | 原因 |
|---|---|---|
| `x/v/bg/ba`、gravity、calibration state、covariance | 必须 | 下一轮 propagation、residual 与 gating 的递归 seed |
| window/clones、landmark/map state、observation history | 必须 | 决定可见约束、triangulation、anchor 与 marginal set |
| factor add/replace/remove、variable timestamp、slot/index map | 必须 | 它们是 graph history，不是 optimizer 的无状态输入 |
| relinearization/delta 与 marginal prior | 必须 | 已压缩的历史依赖 candidate 自己的线性化点和淘汰顺序 |
| keyframe gate state 与 accepted schedule | 必须 | 决定何时产生 state、factor、PIM boundary 和 map event |
| landmark admission、outlier、cull/evict/drop decision | 必须 | 会改变未来 track set、IDs、map 与 graph topology |
| tracker KLT/descriptor/reference frame、feature DB、ID allocator | 条件必需 | 只要接收 candidate pose/map/bias/cull 反馈，就必须分叉 |
| failure/retry/reset/segment/reanchor lifecycle | 必须 | 决定状态连续性、prior 是否仍有效及输出覆盖率 |
| trajectory/output acceptance state | 必须 | 只能从 candidate 已接受状态生成，不能拼接 production fallback |
| 原始/rectified image、IMU samples、静态 calibration/config | 可共享 | 前提是 immutable、同序、无共享 mutable cache |
| 已生成的 tracks/feature packet | 仅条件共享 | 共享后结论只能是 track-conditioned backend counterfactual |

## Shadow trajectory 的解释边界

| Shadow 形态 | 可回答的问题 | 不可声称 |
|---|---|---|
| production factors + production initial values + alternative optimizer | 同一数值问题上 optimizer 行为是否不同 | candidate production trajectory |
| production graph events + candidate 自有 smoother history | 固定 admission/schedule 下，candidate backend 的递归响应 | 替换后 schedule/map/tracks 不变 |
| production tracks + candidate 自有 gate/estimator/map | 给定 production measurement stream 的 backend counterfactual | whole-pipeline ATE / handoff readiness |
| immutable sensor split + candidate 自有 frontend/gate/estimator/lifecycle | 离线、确定性条件下的 production replacement counterfactual | 未验证实时调度、资源竞争或部署行为 |

要把最后一类 trajectory 纳入 VIO-vs-VO gate，还需同时满足：时间轴和 coverage 可比、candidate 无 production pose/bias/map fallback、reset/失败被显式记录、trajectory 来自 candidate accepted states、重复运行确定性成立。否则 ATE 数字可能只是幸存区间或混合轨迹。

## 对 phad-vio P1 的判定

**本地事实**：`apps/offline_vo_session.cpp` 当前因果链是 tracker `process` → `KeyframeEpochGate::decide` → estimator `update`；estimator rotation 回写 gate，culled/evicted track IDs 又经 `StereoTracker::dropTracks/markEvictable` 改变下一帧前端。现有 P1 fixed-lag shadow 位于 estimator 内，消费 production 形成的测量、初值和 graph admission。P1 result 已证明 production artifacts 不变且 shadow 数值链可运行，但其文档也明确不把 shadow delta 当 ATE 或 handoff 依据。

**结论**：P1 是合格的 read-only optimizer diagnostic，不是 candidate-owned closed loop。其差值同时受 production schedule、landmark admission/cull、初值与已形成 prior 约束，不能归因成“切换 estimator 后的轨迹变化”。

## P2 最小可行 seam

若目标是可参与 accuracy gate 的 candidate trajectory，建议在 `apps/` composition root 增加一个窄的 `CandidatePipeline`，分叉点放在 stereo rectification 与 IMU packetization 之后：

1. production 和 candidate 收到相同的只读 rectified frames、IMU packet、calibration/config；candidate 结果绝不回写 production。
2. `CandidatePipeline` 自有 `StereoTracker`、`KeyframeEpochGate`、candidate estimator、track ID/lifecycle、pending/zombie/cull policy、trajectory 与 diagnostics。
3. candidate estimate 只反馈自己的 gate、propagation/association 和 cull；candidate graph events、initial values、relinearization、marginal prior不能从 production 复制。
4. 先用“同实现 twin”验证 seam：同输入下 production/candidate 的 schedule、track lifecycle、accepted states 与 trajectory 应确定性一致；再替换 candidate backend。故意注入一次 candidate-only perturbation 后，后续 schedule/tracks 应允许合理分叉，且 production artifacts 保持 byte-identical。
5. probe 输出显式标记 `ownership=full_pipeline` 或 `ownership=track_conditioned`；只有前者且 coverage/reset 门通过时才生成可用于 VIO-vs-VO 判断的 candidate trajectory。

**最小性说明**：不建议先建立通用多 pipeline 框架；一个 CLI/probe 专用的 composition-root owner 足够。若实施成本要求先在 `FrameTracks` 后分叉，可作为 P2a 数值诊断，但名称、sidecar schema 和结论都必须保留 `track_conditioned`，不得升级为 accuracy counterfactual。

## 证据缺口与验证要求

- 未发现上述项目在同一进程内实现与 phad P2 完全相同的 read-only dual-pipeline shadow；本文 ownership 边界是由其状态流和反馈路径推导，不是直接照搬现成 API。
- 固定 revision 证明“哪些状态参与闭环”，不证明 phad 的具体 seam 一定无遗漏；实现 P2 前仍需用本地 call graph 和 mutation audit 核对 shared objects，特别是 OpenCV image alias、tracker ID allocator 与诊断缓存。
- 异步系统的线程调度也可能改变 event order；本文只为 phad 当前离线顺序执行给出 counterfactual 条件，不覆盖实时并发等价性。
- P1 数据不能分离 optimizer、marginal prior、schedule 与 cull 各自的因果贡献；需要 P2 的 twin-equivalence、candidate-only perturbation 和独立轨迹评测才能关闭证据链。
- 外部论文提供系统结构和算法依据；关键 ownership 判断主要依赖固定 commit 源码。若链接对应仓库后续迁移或镜像消失，应按记录 hash 重新取证，不以浮动 `main` 替代。
