## 问题陈述（phad-vio）

`StereoVoEstimator` 在 BA 后做 VINS 式 mean-reproj cull：从 `landmarks_W` 擦除、清窗口观测；
**不**通知 frontend 丢 track。同一 `LandmarkId` 稍后被当作新点 stereo-backproject ——
「伪永久 / rebirth」。EuRoC MH_01 上与灾难性 BA（reproj RMS ~511 **px**）相关；
`culled_ids_` 拒绝复生可止崩，但 ATE 仍 ~0.72 m（无 cull 基线 ~0.099 m）。

核心对照问题：各系统删除后端 landmark 后，前端同 ID 再出现时会发生什么？

## 3. 对 phad-vio 的含义（仅建议，不改代码）

### 3.1 为何 VINS MT=1 能「忍」复生，而我们崩得更惨？

同型点：后端删、前端不删、同 ID 再进 → 新几何状态。

差异（有利于 VINS、不利于当前 phad cull）：

| 维度 | VINS MT=1 | phad-vio（现状描述） |
|---|---|---|
| 状态参数化 | 窗口内**逆深度**（宿主帧）；复生 `estimated_depth=-1` 再三角化 | `landmarks_W` **世界系 XYZ**；stereo-backproject 一次成形 |
| 复生后立刻进优化的观测 | 仅从新 `start_frame` 起累积；`used_num<4` 时 cull 跳过 | 窗口 BA 立刻可见；坏深度 × 多帧因子 → 残差可到数百 px |
| 先验 | marg prior 吸收旧信息（软）；删点在 `optimization()` **之后** | 无 marg；删点更「干净」但也无缓冲 |
| 鲁棒核 | 优化内 Huber 等 | 有 Huber，但坏初值/错深度仍可把 RMS 拉炸 |
| 失败处理 | `failureDetection()` **写死 return false** | 无对等「吞失败」；数值爆炸直接暴露 |

因此：**「VINS 默许伪永久」≠「XYZ 字典同 ID 硬重生在无 marg 窗口 BA 上安全」**。Basalt/Kimera/OpenVINS 的复生也大多落在 **inv-depth / smart-factor / EKF landmark**，不是「擦掉 `map[id]` 再塞一个新 Vector3d」的同一失败面。

### 3.2 推荐模式（按与本仓库架构契合度）

1. **Track ≠ Landmark（lk-vio / ORB 指针模型）— 最干净**  
   Frontend 只发 track/observation 身份；backend 分配 `LandmarkId`（或内部句柄）。Cull 只杀 landmark；若需续用观测，**发新 ID** 或重新三角化到新句柄。避免 estimator↛frontend 回写。

2. **软信号 / 同步删 track（VINS MT=0）**  
   若坚持 frontend 拥有 `LandmarkId`：composition root 把 `culled_ids` 回传 frontend（单向依赖仍成立），从 track 表移除。与「无 frontend←estimator 库依赖」不冲突——信号走 app 层。

3. **Reject list（你们已验证能止崩）**  
   同 VINS 所缺、你们已加的防护。代价：长期占用「已 cull ID」，前端仍浪费算力跟踪无用点；ATE 仍差说明 **cull 本身/阈值/时机** 仍有问题，不能单靠拒复生回到 0.099 m。

4. **显式重生但换几何宿主（Basalt / VINS MT=1 / Kimera）**  
   若保留同 ID：复生必须等价于「新宿主帧 + 新深度/新 factor」，且 **冷却期**（VINS：`used_num>=4` 才再评估；OpenVINS：`update_fail_count`）避免刚重生就被同一坏几何再次污染。对 phad：至少避免「单帧 stereo backproject XYZ 立刻满窗口因子」。

5. **不建议**：无冷却、无前端通知、同 ID 写入 `landmarks_W` 的裸伪永久——这正是 MH_01 RMS~511 px 的危险合同。

### 3.3 与 Slice ④ 既有结论的衔接
