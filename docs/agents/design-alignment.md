# 设计与实现对齐

本文档描述当前约定，不是绝对约束，会随项目开发修订。

事实源按问题拆开，实现必须从这些文档派生，不得从聊天记忆派生：

- 为什么：[`docs/adr/`](../adr/)
- 系统是什么：[`docs/design/`](../design/)
- 这一片交付什么：[`docs/specs/`](../specs/)
- 怎么执行：[`docs/plans/`](../plans/)

冲突时以 [`docs/design/architecture.md`](../design/architecture.md) 与
[`docs/design/roadmap.md`](../design/roadmap.md) 为准，并回写对应 ADR。

## 定稿标记

- 每条决策/细化点只有两种状态：**「已定稿」**（经用户逐条确认）与**「待讨论」**
  （列出拍板项）。
- 标注「已定稿」的条件：用户明确「同意/认可」；简短回复只覆盖被逐条列出的内容，
  **不扩大解释**。
- 未被逐条确认的内容不得落「已定稿」。

## 实现对齐

- 实现代码必须能回溯到 spec 的验收口径或 design 中的合同。
- 实现偏离设计时：先改文档（走 ADR 回顾），再改代码——禁止代码先行、文档后补。
- 底层代码已演进时，勿直接执行基于旧代码的设计/计划，应重新对齐或重写。

## 决策回顾

- 触发：新的带证据反证（基准数字退化、卡点无法突破、上游生态变化），不是
  「感觉不对」。
- 先区分「决策错误」与「执行不到位」——多数路线失败实为后者。
- 推翻已接受决策时写新 ADR supersede，不改正文改写历史。
- 若建议或实现与已有 ADR 冲突，必须显式指出冲突，不能静默覆盖。
