# 增量开发

本项目按“从无到有、从有到好”开发。先交付最小可运行、可观察、可验证的闭环，
再根据真实需求和问题演进，不提前塑造最终架构。

## 开发顺序

1. 明确当前唯一的外部行为和验收方式。
2. 选择贯通该行为的最短 vertical slice。
3. 编写使其正确工作的最少代码。
4. 运行与风险相称的最小验证。
5. 停止；出现下一项需求或问题证据后再继续。

## 实施原则

- 只实现当前验收条件要求的正常路径和已知失败路径。
- 优先使用具体、直接的实现；第二个真实用例出现后，再按共同需求提取 abstraction。
- 只有完整行为匹配时才复用现有代码；只需要一小部分时，直接实现该部分。
- 不为假想调用方、平台或算法预留配置、工厂、基类、seam 和兼容层。
- 不做没有 profiling 或 benchmark 证据支持的性能优化。
- 不补充与当前闭环无关的重构、测试、文档或格式化。
- 设计不确定时，可用一次性 prototype 回答一个具体问题；不要将其演变为生产框架。
- 重复、失败或维护阻力真实出现后，再小步重构。

## 正确性底线

“最简单可工作”首先必须真实可工作。不得以 YAGNI 或开发速度为由：

- 吞掉错误、静默降级、返回虚假成功或保留空实现；
- 忽略当前已知的不变量、资源生命周期、数学正确性和接口约束；
- 把推测写成事实，或把未执行的验证描述为通过；
- 未经明确授权，破坏已有 public API、数据格式或对外行为；
- 用难以理解的捷径换取少量代码行。

## 决策检查

新增代码、抽象、测试或文档前，只问：

1. 不做它，当前验收是否会失败？
2. 依据是真实需求、可复现失败或测量结果，还是对未来的猜测？
3. 是否有更直接、影响更小且同样正确的实现？

若当前验收不会失败，且没有真实证据，默认推迟。
